# Replay evidence and projection

The reporting service consumes `FieldOps.Core:AuditEvent` from RabbitMQ into its own database. The append-only `audit_events` table retains one logical event per `eventId`. `delivery_attempts` separately records received/processed times, retry number and result; duplicate delivery does not create another business action. `replay_projection` caches the reconstructed current historical state and may be rebuilt by an Administrator without mutating evidence. Operational APIs never replay commands when investigation playback advances.

A separate `fieldops-replay-faults` queue consumes MassTransit's `Fault<AuditEvent>` contract after consumer retry exhaustion. The fault ID is deduplicated in the same database transaction as original-event preservation, append-only `MessageProcessingFailed.v1` / `DeadLetterRecorded.v1` diagnostics, a terminal delivery observation and projection update. Only sanitized exception type names are retained; exception messages, stack traces, Data and host names are excluded. The original payload, occurrence time and hash are never replaced by the later fault's timestamp. Normal delivery may subsequently recover and populate facts without duplicating evidence that the fault monitor already preserved.

Terminal attempt and retry counts are nullable because the fault contract does not provide an authoritative count. Per-consumer processing status can therefore be `DeadLettered`, `PartiallyFailed`, `Processed`, `Failed` or `Unknown`; diagnostic evidence without a business delivery attempt is `EvidenceRecorded`. A delayed terminal observation does not override a later observed recovery for the same consumer. Terminal fault evidence indicates the configured error-routing path; operators still inspect the actual `_error` queue before claiming that a particular message is retained or repaired.

`AuditEvent` includes event/version IDs, order/workflow/stage IDs, actor/role, source service, correlation/causation, trace/span, authoritative occurrence/recording timestamps, per-source sequence, versioned payload and schema version. Arrival/processing timestamps belong to `StoredEvent`, not the producer's occurrence metadata. Client-reported offline times remain explicitly non-authoritative payload fields. Customer names/addresses are excluded at production of integration events; exports inherit that minimization.

Stored body text preserves original JSON bytes. SHA-256 is verified on investigation reads. Database triggers reject ordinary updates/deletions to both evidence tables, while EF rejects tracked mutations before SQL execution. This is integrity checking and application/database permission protection, not a cryptographically signed immutable ledger: a database superuser could disable triggers and rewrite both evidence and hashes. Protect migration/owner credentials separately from normal application credentials and retain independent backups.

`ReplayEngine.Order` deduplicates event IDs, respects causation and authoritative per-source sequence, then uses occurrence time and event ID to display independent events deterministically. The API marks uncertain cross-service ordering, missing causation and processing delay. Source clock skew never overrides a known causation relationship. Late evidence is appended, then incorporated by rebuilding the mutable projection from the complete retained event set. The immutable record is never rewritten to fake earlier arrival.

Default access is Supervisor for the caller's team, or Administrator. Analysts and technicians cannot open replay. Correlation metadata persists even when Jaeger's trace retention expires; the console must describe unavailable traces without treating that as missing business evidence. Trace IDs alone do not establish a root cause. Incident summaries list observed counts/actions and explicitly avoid inferring operational causes.

No retention deletion job is enabled by default: local portfolio evidence is retained until an authorized administrator removes the development environment. A production deployment needs a documented retention period, encrypted backup/archive destination, legal deletion process, separate archival identity, trace retention settings and audit access reviews. Ordinary application access must never include permission to disable append-only triggers.

Implementation: `building-blocks/FieldOps.Core/ReplayEngine.cs`, `building-blocks/FieldOps.ServiceHost/Messaging.cs`, `ReportingApi.cs`, `Persistence.cs`, and `services/reporting/migrations`.
